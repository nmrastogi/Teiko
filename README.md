# Teiko Clinical Trial – Immune Cell Analysis

A Python pipeline and interactive dashboard for analysing how the drug candidate **miraclib** affects immune cell populations across patient samples from a Loblaw Bio clinical trial.

---

## Quick Start (GitHub Codespaces)

```bash
make setup      # install dependencies
make pipeline   # run full data pipeline (Parts 1–4)
make dashboard  # launch interactive dashboard at http://localhost:8501
```

## Database Schema

### Design

```
projects
  └── project_id  TEXT  PK

subjects
  ├── subject_id  TEXT  PK
  ├── project_id  TEXT  FK → projects
  ├── condition   TEXT          (melanoma / carcinoma / healthy)
  ├── age         INTEGER
  └── sex         TEXT

samples
  ├── sample_id                   TEXT  PK
  ├── subject_id                  TEXT  FK → subjects
  ├── treatment                   TEXT
  ├── response                    TEXT
  ├── sample_type                 TEXT  (PBMC / WB)
  └── time_from_treatment_start   INTEGER

cell_counts
  ├── sample_id   TEXT  PK / FK → samples
  ├── b_cell      INTEGER
  ├── cd8_t_cell  INTEGER
  ├── cd4_t_cell  INTEGER
  ├── nk_cell     INTEGER
  └── monocyte    INTEGER
```

### Rationale

The schema follows a **four-table normalised hierarchy** that mirrors the natural structure of clinical data:

| Table | What it holds | Why separate? |
|---|---|---|
| `projects` | Trial / cohort identifiers | Isolates project-level metadata; adding a new project is a single row insert. |
| `subjects` | Patient demographics (condition, age, sex) | Subject attributes are facts about a *person*, not a *sample*.  Storing them once avoids update anomalies when a field is corrected retroactively. |
| `samples` | Per-collection metadata (treatment, response, time, sample type) | A subject has multiple samples over time.  Keeping collection-time facts here lets you query temporal trends without touching `subjects`. |
| `cell_counts` | Raw cell counts per sample | Separating measurements from metadata keeps each table focused.  New assay types (cytokine panels, ATAC-seq peaks) can be added as new tables keyed on `sample_id` without altering `samples`. |

**Indexes** on `condition`, `treatment`, `response`, `sample_type`, and `time_from_treatment_start` ensure that the frequent analytical filters used in Parts 3 & 4 run efficiently.

### Scalability

| Dimension | How the schema handles it |
|---|---|
| Hundreds of projects | `projects` table scales linearly; project-level aggregations use indexed joins. |
| Thousands of samples | Foreign-key indexes on `samples` and `cell_counts` keep join performance O(log n). |
| New assay types | Add a new table (e.g. `cytokine_counts`) keyed on `sample_id`; no existing table changes. |
| New metadata fields | Add columns to `subjects` (patient-level) or `samples` (collection-level) as appropriate; neither requires a schema migration on the other tables. |
| Analytics at scale | The schema is compatible with columnar stores (e.g. DuckDB) or a data warehouse (BigQuery, Snowflake) if the SQLite layer is replaced; the same SQL queries work unchanged. |

## Code Structure & Design Decisions

### `load_data.py`
Single-responsibility script that (a) creates the schema and (b) bulk-loads the CSV via Python's `csv.DictReader`.  Uses `INSERT OR IGNORE` so repeated runs are idempotent.  Kept separate from analysis so the database layer can be replaced independently.

### `analysis.py`
Procedural script organised into clearly named functions, one per analytical output:

- **`build_summary_table`** – pivots wide cell-count rows into a long-form (sample × population) table with computed `percentage` column (Part 2).
- **`load_melanoma_miraclib_pbmc`** – SQL query with explicit filters; returns a DataFrame with pre-computed `*_pct` columns ready for statistics.
- **`run_statistics`** – Mann-Whitney U test (non-parametric, no normality assumption) for each of the five populations, followed by Benjamini-Hochberg FDR correction across the five simultaneous tests (Part 3).
- **`plot_boxplots`** – matplotlib figure with one panel per population; annotations show raw and FDR-corrected p-values.
- **`run_part4`** – SQL join query for the baseline subset; aggregations are expressed in pandas for clarity (Part 4).

### `index.html` (D3.js dashboard)
Single-file static dashboard served by Python's built-in HTTP server (`python3 -m http.server 8080`).  No additional server-side framework required.  Key decisions:

- **D3.js v7 from CDN** – loaded at runtime; no build step needed.
- **Three JSON files** exported by `analysis.py` and loaded client-side via `d3.json()`.  Data is pre-aggregated at pipeline time so the browser only receives what it needs.
- **Filters in Part 2** – condition, treatment, sample type, and population dropdowns filter the full 10,500-sample dataset entirely in-browser with instant response.
- **Client-side boxplot statistics** – Q1, Q3, IQR, and whiskers are computed in JavaScript from the raw percentage arrays, keeping the Python export simple.
- **Part 4 charts** – a D3 donut chart for project breakdown and grouped bar charts for response/sex counts, with a highlighted metric card for the average B-cell answer.

### Statistical methodology (Part 3)

The **Mann-Whitney U test** was chosen because:
1. It makes no assumption about the distribution of relative frequencies.
2. It is robust to outliers and small group sizes.
3. It is the standard non-parametric alternative to the two-sample t-test.

Five tests are run simultaneously (one per population), so **Benjamini-Hochberg FDR correction** is applied to control the false-discovery rate at 5 %.  Both raw and corrected p-values are reported so readers can apply their own thresholds.
