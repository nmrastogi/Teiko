# Teiko Clinical Trial – Immune Cell Analysis

A Python pipeline and interactive dashboard for analysing how the drug candidate **miraclib** affects immune cell populations across patient samples from a Loblaw Bio clinical trial.

**Chatbot interface:** [https://teikochat.streamlit.app/](https://teikochat.streamlit.app/) — a natural-language chatbot that queries `teiko.db` directly, letting you ask questions about the trial data in plain English.

---


## Database Schema

### Design

```
projects
  └── project_id  TEXT  PK

subjects
  ├── subject_id  TEXT  PK
  ├── project_id  TEXT  FK → projects
  ├── condition   TEXT          (melanoma / carcinoma / healthy)
  ├── age         INTEGER
  └── sex         TEXT

samples
  ├── sample_id                   TEXT  PK
  ├── subject_id                  TEXT  FK → subjects
  ├── treatment                   TEXT          (miraclib / phauximab / none)
  ├── response                    TEXT
  ├── sample_type                 TEXT          (PBMC / WB)
  └── time_from_treatment_start   INTEGER

> **Note on `treatment = 'none'`:** the value `none` indicates the patient received no active drug (i.e. placebo / control group). It is **not** a missing value. Samples with `treatment = 'none'` are valid observations and are intentionally included in the dataset.

cell_counts
  ├── sample_id   TEXT  PK / FK → samples
  ├── b_cell      INTEGER
  ├── cd8_t_cell  INTEGER
  ├── cd4_t_cell  INTEGER
  ├── nk_cell     INTEGER
  └── monocyte    INTEGER

cell_frequencies
  ├── sample_id   TEXT  PK / FK → samples
  ├── population  TEXT  PK          (b_cell / cd8_t_cell / cd4_t_cell / nk_cell / monocyte)
  ├── count       INTEGER
  ├── total_count INTEGER
  └── percentage  REAL
```

### Rationale

The schema follows a **five-table normalised hierarchy** that mirrors the natural structure of clinical data:

| Table | What it holds | Why separate? |
|---|---|---|
| `projects` | Trial / cohort identifiers | Isolates project-level metadata; adding a new project requires only a single row insert. |
| `subjects` | Patient demographics (condition, age, sex) | Subject attributes are facts about a *person*, not a *sample*. Storing them once avoids update anomalies when a field is corrected retroactively. |
| `samples` | Per-collection metadata (treatment, response, time, sample type) | A subject can have multiple samples across time points. Keeping collection-time facts here enables temporal queries without touching `subjects`. |
| `cell_counts` | Raw cell counts per sample | Separating measurements from metadata keeps each table focused. New assay types (e.g. cytokine panels, ATAC-seq peaks) can be added as new tables keyed on `sample_id` without altering `samples`. |
| `cell_frequencies` | Pre-computed relative frequencies (count, total, percentage) per population per sample | Materialised at load time so the dashboard and analysis queries read directly from this table rather than recomputing on every request. 52,500 rows (10,500 samples × 5 populations). |

**Indexes** on `condition`, `treatment`, `response`, `sample_type`, and `time_from_treatment_start` ensure that the frequent analytical filters used in Parts 3 & 4 run efficiently.

### Scalability

| Dimension | How the schema handles it |
|---|---|
| Hundreds of projects | `projects` table scales linearly; project-level aggregations use indexed joins. |
| Thousands of samples | Foreign-key indexes on `samples` and `cell_counts` keep join performance O(log n). |
| New assay types | Add a new table (e.g. `cytokine_counts`) keyed on `sample_id`; no existing table changes. |
| New metadata fields | Add columns to `subjects` (patient-level) or `samples` (collection-level); neither change requires a migration on the other tables. |
| Analytics at scale | The schema is compatible with columnar stores (e.g. DuckDB) or a cloud data warehouse (BigQuery, Snowflake) if the SQLite layer is replaced; the same SQL queries work unchanged. |

## Code Structure & Design Decisions

### `load_data.py`
Single-responsibility script that (a) creates the schema and (b) bulk-loads the CSV via Python's `csv.DictReader`. Uses `INSERT OR IGNORE` so repeated runs are idempotent. After loading raw counts it populates `cell_frequencies` via a single SQL `UNION ALL` unpivot — no Python loop required. Kept separate from analysis so the database layer can be replaced independently.

### `analysis.py`
Procedural script organised into clearly named functions, one per analytical output:

- **`build_summary_table`** – queries `cell_frequencies` directly; returns a long-form (sample × population) DataFrame with count, total, and percentage columns (Part 2).
- **`load_melanoma_miraclib_pbmc`** – applies explicit SQL filters; returns a DataFrame with pre-computed `*_pct` columns ready for statistical testing.
- **`run_statistics`** – Mann-Whitney U test (non-parametric, no normality assumption) for each of the five populations; significance determined at α = 0.05 on raw p-values (Part 3).
- **`plot_boxplots`** – matplotlib figure with one panel per population; annotations show the raw p-value and significance stars.
- **`run_part4`** – SQL join query for the baseline subset; aggregations are handled in pandas for clarity (Part 4).

### `server.py` (Flask API)
Flask application that serves the D3.js dashboard and exposes parameterised API endpoints, each querying `teiko.db` directly at request time — no pre-generated JSON files required.

All three data endpoints accept query parameters so the database does the filtering and aggregation; the browser never receives data it does not need.

| Endpoint | Parameters | What the server computes |
|---|---|---|
| `GET /api/initial-analysis` | `condition`, `treatment`, `sample_type`, `time`, `response`, `sex`, `population` | SQL `WHERE` clause built from params; returns only matching rows |
| `GET /api/initial-analysis/opts` | — | Distinct values for each Initial Analysis dropdown |
| `GET /api/statistical-analysis` | `condition`, `treatment`, `sample_type` | Mann-Whitney U p-values; **boxplot quartiles (Q1, median, Q3, whiskers, outliers) computed in SQL** via `ROW_NUMBER()` window functions and a CTE chain — no JavaScript arithmetic |
| `GET /api/data-subset-analysis` | `condition`, `sample_type`, `time`, `treatment` | Aggregated counts and avg B-cell for male responders |
| `GET /api/data-subset-analysis/opts` | — | Distinct values for each Data Subset Analysis dropdown |

### `index.html` (D3.js dashboard)
Single-file dashboard with three tabs, loaded from CDN — no build step required. Key design decisions:

- **API-based filtering** — the dashboard never loads the full dataset into memory. On page load only the dropdown option lists are fetched. Every filter change sends the selected parameters to the server as query params; the API filters in SQL and returns only the matching rows. This keeps the browser payload small regardless of how large the underlying dataset grows.
- **Initial Analysis (Tab 1)** – seven filter dropdowns (condition, treatment, sample type, time point, response, sex, population); changing any dropdown triggers a new `GET /api/initial-analysis?…` request. Results are shown in a paginated table and an average-frequency bar chart.
- **Statistical Analysis (Tab 2)** – three filter dropdowns (condition, treatment, sample type); changing any dropdown re-fetches `/api/statistical-analysis?…`. The server returns pre-computed boxplot statistics (Q1, median, Q3, whisker bounds, outlier points) computed entirely in SQL — the browser only draws the SVG shapes.
- **Data Subset Analysis (Tab 3)** – four dropdowns (condition, sample type, time point, treatment) trigger a live re-fetch of `/api/data-subset-analysis?…`; results update a donut chart (samples per project), two bar charts (subjects by response and by sex), and the average B-cell count for male responders (computed using only condition and time — not filtered by sample type or treatment, to match the literal question).

### Boxplot whiskers — valid data range

Each boxplot follows the **Tukey fence** convention:

- **Box** spans Q1 to Q3 (the interquartile range, IQR).
- **Median line** marks the 50th percentile inside the box.
- **Whiskers** extend from the box to the most extreme data point that still falls within **1.5 × IQR** of the box edges:
  - Lower whisker = smallest value ≥ Q1 − 1.5 × IQR
  - Upper whisker = largest value ≤ Q3 + 1.5 × IQR
- **Dots beyond the whiskers** are individual outliers — observations outside the valid range defined by the fences.

The whiskers therefore represent the **valid range of typical data**. Any point outside them is unusually high or low relative to the bulk of the distribution and is plotted individually. Quartiles, whisker bounds, and outlier values are all computed server-side in SQL before being sent to the browser.

### Statistical Methodology (Part 3)

**Significance threshold:** α = 0.05 applied directly to raw p-values.

**Test: Mann-Whitney U (two-sided)** was chosen because:
1. It makes no assumption about the distribution of relative frequencies (non-parametric).
2. It is robust to outliers and unequal group sizes.
3. It is the standard non-parametric alternative to the two-sample t-test for comparing two independent groups.

**Result:** CD4 T Cell is the only population that approaches significance (p = 0.0133). No other population reaches α = 0.05. All raw p-values are reported so readers can apply their own thresholds.

## Tests

Tests live in [tests/test_data.py](tests/test_data.py) and run against an in-memory SQLite database, so they are fast and leave no files on disk.

```bash
make test
# or directly:
pytest tests/test_data.py -v
```

### Duplicate data tests

| Test | What it verifies |
|---|---|
| `test_duplicate_sample_same_file_ignored` | Same row twice in one CSV → only 1 row inserted (`INSERT OR IGNORE`) |
| `test_load_same_csv_twice_idempotent` | Loading the same CSV a second time leaves row counts unchanged |
| `test_duplicate_subject_across_samples` | Same subject with two different samples → 1 subject, 2 samples |
| `test_duplicate_project_not_duplicated` | Multiple samples in the same project → 1 project row |
| `test_duplicate_sample_different_counts_keeps_first` | Same `sample_id` with different cell counts → first inserted wins |
| `test_populate_frequencies_idempotent` | Calling `populate_frequencies` twice → still exactly 5 rows per sample |

### Bad data tests

| Test | What it verifies |
|---|---|
| `test_missing_csv_file_raises` | Non-existent CSV path → `OSError` |
| `test_non_integer_cell_count_raises` | `b_cell="not_a_number"` → raises and fully rolls back the transaction |
| `test_non_integer_age_stored_as_null` | Blank `age` field → stored as `NULL` without error |
| `test_missing_response_stored_as_null` | Blank `response` field → stored as `NULL` without error |
| `test_missing_required_column_raises` | CSV missing the `sample` column → `KeyError` |
| `test_negative_cell_count_inserted` | Negative count → stored as-is (schema has no CHECK constraint) |
| `test_empty_csv_no_rows_inserted` | Header-only CSV → 0 rows inserted across all tables |
| `test_frequencies_percentages_sum_to_100` | Percentages for one sample sum to exactly 100% |
| `test_frequencies_correct_values` | Known cell counts produce the correct percentage values |

## Limitations & Future Work

The current implementation is well-suited for the scale of this dataset (10,500 samples, 5 cell populations, a single CSV file). Several design choices would need to change at production scale:

### Data ingestion

**Row-by-row CSV loading** — `load_data.py` inserts one row at a time inside a Python loop. This is simple and correct for small files, but degrades linearly with input size. At scale, two improvements apply:

- **Batch inserts** — group rows into chunks (e.g. 10,000 at a time) and use `executemany` with a single prepared statement per batch. This reduces per-row Python overhead and SQLite transaction cost by an order of magnitude.
- **Distributed ingestion with Apache Spark** — for files in the hundreds of GBs or multi-file ingestion pipelines, PySpark's `DataFrameWriter` can write directly to a data warehouse (BigQuery, Snowflake, Delta Lake) in parallel, bypassing the SQLite layer entirely. The normalised schema maps cleanly onto partitioned columnar tables, and the same SQL queries used here continue to work unchanged.

### Database engine

**SQLite** is an embedded, single-file database — appropriate for local analysis and reproducible research, but not designed for concurrent writes or datasets that exceed available RAM. A production deployment would replace it with:

- **PostgreSQL or DuckDB** for single-server analytics with better concurrency and columnar query optimisation.
- **BigQuery or Snowflake** for cloud-scale multi-user access, with partitioning on `condition` and `time_from_treatment_start` to keep analytical queries fast.

### API & dashboard

**Flask development server** (`app.run`) is single-threaded and not suitable for concurrent users. A production deployment would front it with **Gunicorn** (multi-worker WSGI) or migrate to an async framework (FastAPI). All filtering is already server-side — the browser only receives the rows matching the selected parameters. At larger scales, the API could additionally support cursor-based pagination so even filtered result sets are streamed rather than sent in a single response.

### Statistical analysis

The Mann-Whitney U test is appropriate for the current five-population, two-group comparison. Extending the analysis to more populations, more groups, or longitudinal modelling (e.g. mixed-effects models across time points) would require a more structured statistical pipeline — likely in R (using `lme4` or `DESeq2`) or Python (using `pingouin` or `statsmodels`).

### Row updates

The loader uses `INSERT OR IGNORE`, which silently discards any row whose primary key already exists. This makes repeated pipeline runs safe and idempotent, but it means **corrections to source data are never applied** — if a patient's `response` or a sample's `treatment` is amended in the CSV, re-running the pipeline will not update the database.

To support updates, inserts would need to be replaced with upserts using SQLite's `ON CONFLICT … DO UPDATE` clause:

```sql
INSERT INTO samples (sample_id, subject_id, treatment, response, sample_type, time_from_treatment_start)
VALUES (?, ?, ?, ?, ?, ?)
ON CONFLICT(sample_id) DO UPDATE SET
    response  = excluded.response,
    treatment = excluded.treatment;
```

Any sample whose cell counts change would also require `cell_frequencies` to be recomputed for that `sample_id`. Without this, the pre-aggregated percentages would be stale.

### Schema constraints

The `cell_counts` table has no `CHECK` constraint preventing negative counts, and the `samples` table does not enforce a controlled vocabulary on `treatment` or `condition`. Adding these constraints at the DDL level would catch bad data at insert time rather than requiring downstream validation.
